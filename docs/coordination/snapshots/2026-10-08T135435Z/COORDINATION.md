# Правила совместной работы Codex и Claude

## Общий контекст

Оба агента читают текущий `LATEST.json` и соответствующий снимок перед работой. После завершения задачи обновляют статус, изменённые файлы, commit/hash, проведённые проверки и ограничения. Не считать память отдельного чата источником текущей версии.

Cloud Claude читает ветку `sync/codex-claude-context` основного GitHub-репозитория. Это ветка обмена и снимка, НЕ production/main и НЕ разрешение деплоя. Локальный Claude Code также может читать `C:\Users\BANGKOK PC\raidos-claude-sync`.

## Один владелец изменений

1. Перед началом записать в рабочем логе цель, agent, branch, baseCommit и ownedFiles. Статус `in_progress` объявляется только после фактического начала.
2. Если файлы пересекаются с активной задачей второго агента, выбрать другую задачу или согласовать передачу. Не редактировать одновременно `electron/main.ts`, `electron/experimental/index.ts`, `App.tsx`, story sync или auth.
3. Работать в отдельных ветках/копиях. Не использовать общий грязный production checkout для разработки.
4. Сохранять пользовательские изменения. Только non-destructive Git; никаких force-push, reset --hard или широких удалений.
5. Изменения выдавать как небольшой commit/PR с тестами и точным списком файлов. Второй агент делает review до интеграции.
6. Обновление общего контекста не означает запуск Claude, сообщение в чужой чат или установление API-соединения. Прямого канала Claude в этом сеансе нет.

## Разделение ролей по умолчанию

Codex: интеграция, native Electron/Windows, сборка, публикация и эксплуатация VPS. Claude: независимый анализ story/OCR/catalog и frontend/security review. Это предложение, роли меняются по конкретной задаче владельца.

Только один интегратор/издатель одновременно. По умолчанию Codex. Claude не деплоит параллельно и не запускает сборку в live root, пока другой агент публикует.

## Как восстановить snapshot-код

В новом чистом clone проверить базовый commit из `source-manifest.json`. До наложения архива проверить его file hashes. `source-overlay.tar.gz` содержит новые файлы и замены; `tracked-changes.patch` включает только отслеживаемые изменения. Не применять одновременно diff и те же замены.

Общая ветка `sync/codex-claude-context` уже содержит эти исходники. При работе из неё архив повторно не применять. Новые признаки изменений внутри этой ветки не равны новым опубликованным build.

Действия `delete` из manifest требуют осмысленного удаления только указанного файла в чистом baseline checkout. Перенос архива в папку с чужими изменениями запрещён.

На Windows сохранить точный регистр путей. Архив содержит источники, не `node_modules`, traineddata, картинки cache или EXE; дополнительные ресурсы брать из базового репозитория/проверенного build environment.

## Release checklist

1. Перед запуском сверить source hashes, текущий deploy и доступность сервера. При расхождении не перетирать новый код.
2. Создать согласованный SQLite backup; держать user data отдельно от кода и релизов.
3. Собрать и протестировать в staging. Сохранять client/owner editions, OCR traineddata, Windows native module, public entitlement key.
4. Проверить unit/component/native scopes соразмерно изменению; явно указать непроверенное.
5. Подписать клиентский манифест доверенным приватным ключом НА сервере, без вывода ключа. Проверить size/hash/signature.
6. Резервировать предыдущие EXE/manifest, атомарно публиковать EXE, затем новый manifest. Не раздавать owner EXE публично.
7. Проверить direct attachment, 206/MZ, signed manifest, API/database, сайт и маршруты.
8. Ошибка: откатить код/релиз, не заменяя рабочую пользовательскую базу старым снимком. Если миграция несовместима, не импровизировать восстановлением поверх новых данных.
9. Записать реальную build id и commit; суффикс сборки не выдавать за новый Git-коммит.

## Постоянная синхронизация

- После каждой выполненной задачи: событие, код, tests, deployment status и next steps в рабочий лог/общий контекст.
- Раз в час: read-only probe Git refs, source hashes, публичной версии и здоровья API. Без изменений молчать и не создавать лишние snapshots.
- Изменение: создать новый неизменяемый snapshot, проверить его, обновить LATEST/пакет/общую ветку без перезаписи чужого dirty checkout.
- Ошибка или занятая рабочая копия: сохранить предыдущий snapshot, не force-push и не стирать работу; сообщить о необходимом вмешательстве.
- Монитор не меняет код работающего сервера, оплату, аккаунты, права, firewall, Windows tasks или настройки секретов. Он не возвращает 15-минутный deploy-agent.
- Локальная автоматизация зависит от доступности этого ПК и приложения Codex; не обещать круглосуточный запуск при выключенном ПК. Никакого daemon на VPS для этого пакета не установлено.

## Секреты и доступ

Не включать `.env`, пароли аккаунтов/SSH, session tokens, private keys, live DB/WAL/SHM, payment credentials или private logs. Публичные ключи допустимы. Тестовые fixture passwords не принимать за реальные данные.

Если выявлен реальный секрет в source snapshot, прекратить публикацию и сообщить о необходимости ротации, не печатая секрет. Контроль шаблонов не заменяет review.

Внешний агент получает код/контекст, не root SSH права автоматически. Для доступа требуются отдельно настроенные ограниченные полномочия. Не использовать режим обхода всех permissions для обычной парной работы.
