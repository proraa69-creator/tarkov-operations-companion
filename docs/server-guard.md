# Страж сервера

«Страж сервера» следит за сервером Raid OS на ноутбуке владельца: отбивает подозрительные запросы, сам
перезапускает API при ошибках, каждый день делает резервную копию базы и сообщает владельцу о проблемах.

Из чего состоит:

| Часть | Где | Что делает |
| --- | --- | --- |
| Охрана запросов | `server/src/services/securityGuard.ts` | считает подозрительные запросы по адресам посетителей, блокирует |
| Здоровье API | `server/src/services/serverHealth.ts` | ошибки 5xx, задержка, память, проверка базы, необработанные ошибки |
| Резервные копии | `server/src/services/serverBackups.ts` | копия базы `VACUUM INTO`, хранение 14 дней |
| Подключение к API | `server/src/routes/serverGuard.ts` | `/health/detail`, `/health/backup`, API вкладки «Безопасность» |
| Наблюдатель в приложении | `electron/serverGuardian.ts`, `electron/serverMonitor.ts` | перезапуски, ежедневные копии, уведомления, лампа «Безопасность» |
| Админ-панель сайта | `website/src/components/admin/AdminSecurity.tsx` | вкладка «Безопасность» |

## Что считается подозрительным

Адрес посетителя — тот, что передал сайт-прокси (`X-Forwarded-For`) или Cloudflare (`CF-Connecting-IP`).
Каждое подозрительное действие даёт очки. Если за 10 минут набирается 100 очков, адрес блокируется.

| Причина | Пример | Очки |
| --- | --- | --- |
| Сканирование уязвимостей | `/.env`, `/.git/config`, `/wp-login.php`, `/phpmyadmin`, `/cgi-bin/…`, любые `*.php` | 35 за запрос (3 запроса — блокировка) |
| Обход путей | `..` в адресе, в том числе закодированные `%2e%2e`, `%252e`, `..%2f` | 50 |
| SQL или скрипт-инъекции | `' or '1'='1`, `UNION SELECT`, `<script`, `${jndi:`, `/etc/passwd` в параметрах или в теле запроса | 35 |
| Перебор адресов (404) | первые 30 ответов 404 за 10 минут бесплатно, дальше | 4 |
| Отказы в доступе (401/403) | первые 20 бесплатно (истёкший вход бывает у всех), дальше | 5 |
| Превышение лимитов (429) | первые 30 бесплатно, дальше | 3 |
| Неудачные входы | первые 8 бесплатно, дальше | 10 |
| Подбор паролей по многим e-mail | неудачные входы на 6 и больше разных e-mail с одного адреса за 15 минут | 100 (сразу блокировка) |
| Слишком большие запросы | тело больше 1 МБ (ответ 413) | 25 |

Правила намеренно осторожные:

- Обычные пути API и сайта никогда не дают очков. Тест `server/src/routes/serverGuard.test.ts` проверяет все пути API
  с настоящими параметрами и телами, в том числе пароли со странными символами и ники вроде `Select_Union`.
- Пароли, коды и токены не проверяются на инъекции. Личные документы пользователя (`/v1/me/…`: настройки, заметки,
  Коллекционер) тоже не проверяются.
- Сайт не отдаёт сканерам свою главную страницу. Запросы вроде `/.env` или `*.php` сайт передаёт API: охрана начисляет
  очки и отвечает 404 (`electron/siteProxy.ts`).

## Блокировки

- Заблокированный адрес сразу получает ответ 403, до любой обработки. Такие запросы не пишутся в базу, их только
  считают.
- Срок растёт, если адрес блокируют повторно в течение 7 дней: **15 минут → 1 час → 24 часа**. После недели без
  блокировок счёт начинается заново.
- **Никогда не блокируются:**
  - этот компьютер (`127.0.0.1` и `::1`), в том числе браузер владельца, открывший сайт через `localhost:5202`;
  - прямые запросы приложения к API;
  - адреса из белого списка. Их можно добавить в админ-панели или в переменной `TARKOV_GUARD_ALLOWLIST`
    (адреса через запятую).
- Если владелец вошёл в аккаунт, его запросы проходят даже с заблокированного адреса. Так он всегда может снять
  блокировку с сайта.
- Блокировки переживают перезапуск сервера.

### Что хранится

Таблицы `security_events`, `security_bans`, `security_allowlist` и `security_meta` лежат в той же базе
`companion.sqlite`. Сервер создаёт их сам, остальные таблицы он не трогает.

Хранится:

- маскированный адрес (`203.0.113.*`, у IPv6 — первые три группы);
- солёный хеш адреса, чтобы узнавать заблокированный адрес;
- путь без параметров;
- причина, число повторов и время.

Не хранится: полный адрес, тела запросов, параметры, e-mail, пароли, токены.

События удаляются через 30 дней. Завершённые блокировки тоже удаляются через 30 дней.

## Самопроверка и самовосстановление

API отдаёт подробное здоровье только этому компьютеру: `GET http://127.0.0.1:8787/health/detail`. Через сайт или
публичный адрес этот запрос получает 404. Наблюдатель в приложении-сервере читает его каждые 15 секунд и действует
так:

| Что видит | Что делает |
| --- | --- |
| За 5 минут не меньше 20 ответов 5xx, и это не меньше 50% всех ответов | копия базы → перезапуск API |
| 3 необработанных исключения за 5 минут | копия базы → перезапуск API |
| Задержка обработки (p99) больше 1 секунды 3 проверки подряд | копия базы → перезапуск API |
| Память больше 1,5 ГБ или выросла в 3 раза (и больше 768 МБ) | копия базы → перезапуск API |
| За 15 минут не меньше 10 ответов 5xx, и это не меньше 20% всех ответов | уведомление «Сервер: много ошибок» |
| API упал 4 раза за 30 минут | уведомление «Сервер падает снова и снова» |
| Проверка базы `PRAGMA quick_check` не прошла (API проверяет раз в час) | красная лампа «База данных» и уведомление с инструкцией |

Защита от зацикливания: перезапуск из-за ошибок бывает не чаще раза в 15 минут и не больше 3 раз за 6 часов. Потом
автоматические перезапуски приостанавливаются, а владелец получает уведомление «Сервер: нужна ваша помощь». Если
процесс API просто остановился, его, как и раньше, перезапускает обычный наблюдатель с паузами 5 с → 15 с → 60 с →
5 мин.

Необработанные исключения и отклонённые промисы пишутся в `api.log` вместе со стеком, и API их считает. Процесс при
этом продолжает работать: если ошибки повторяются, его перезапустит наблюдатель, предварительно сделав копию базы.

## Уведомления

Уведомление приходит в Windows и всплывает внутри приложения. Каждый вид уведомления ограничен по частоте.

| Уведомление | Как часто, не чаще |
| --- | --- |
| «Сервер отбил подозрительные запросы» (сводка, не по одному запросу) | раз в 30 минут |
| «Сервер: много ошибок» | раз в 30 минут |
| «Резервная копия не создана» | раз в 6 часов |
| «База данных: возможно повреждение» | раз в 6 часов |
| «Сервер падает снова и снова» | раз в час |

Раз в сутки в журнале наблюдателя («Журнал» под лампами и файл `watchdog.log`) появляется строка
«Сводка за сутки». В ней:

- запросы и ошибки;
- заблокированные адреса;
- память;
- размер базы и результат её проверки;
- время последней резервной копии.

## Где это видно

- **Приложение-сервер**, Профиль → лампы состояния, строка «Безопасность»:
  - зелёная — спокойно;
  - жёлтая — были подозрительные запросы или есть активные блокировки;
  - красная — идёт атака: 3 и больше блокировок за час или подбор паролей.

  Кнопка «Админ-панель» открывает вкладку «Безопасность» на сайте.
- **Сайт → Админ-панель → «Безопасность»** (`/admin?tab=security`). Вкладка доступна только владельцу: сервер
  проверяет это сам и всем остальным отвечает 404. На вкладке:
  - состояние;
  - активные блокировки с кнопкой «Снять» и форма ручной блокировки на 1 час, 24 часа, 7 или 30 дней;
  - причины за сутки и журнал подозрительных запросов;
  - график ошибок 5xx за 24 часа или за 2 часа;
  - память, задержка, размер базы и её проверка;
  - последняя резервная копия;
  - белый список.

## Резервные копии

- Копии лежат в папке `backups` рядом с базой: `%APPDATA%\Tarkov Operator\server\backups\`.
- Каждый день приложение-сервер просит API сделать копию `companion-daily-<дата>.sqlite`. Если копии нет больше
  суток, она делается при следующей проверке. Если не получилось, приложение повторяет попытку через час и
  сообщает владельцу.
- Перед каждым перезапуском из-за ошибок делается копия `companion-before-restart-<дата>.sqlite`.
- Копии хранятся 14 дней. Три самые новые не удаляются никогда, даже если они старше.
- Чужие файлы в папке не трогаются. Это касается и ручных копий `npm --prefix server run backup`.
- Копию делает сам API командой `VACUUM INTO`. Это согласованный снимок, сервер при этом не останавливается.

## Как восстановить копию

Приложение **никогда не восстанавливает базу само**: замена данных — решение владельца.

1. В приложении-сервере откройте Профиль и выключите «Сервер и сайт на этом компьютере». Можно просто закрыть
   приложение.
2. Откройте папку `%APPDATA%\Tarkov Operator\server\`.
3. Перенесите текущие `companion.sqlite`, `companion.sqlite-wal` и `companion.sqlite-shm` в отдельную папку,
   например `broken-<дата>`. Не удаляйте их: они могут понадобиться.
4. Возьмите в `backups\` нужную копию. Обычно это последняя `companion-daily-…` или `companion-before-restart-…`.
   Скопируйте её в `%APPDATA%\Tarkov Operator\server\` и переименуйте в `companion.sqlite`. Файлов `-wal` и `-shm`
   рядом быть не должно.
5. Включите сервер снова и проверьте лампы. Лампа «База данных» должна быть зелёной, а через час проверка базы на
   вкладке «Безопасность» должна показать «в порядке».

Всё, что изменилось после времени копии, пропадёт: новые регистрации, оплаты, прогресс. Сверьте последние платежи с
кабинетом платёжного сервиса. Подписку, которая потерялась, можно выдать вручную в админ-панели: «Пользователи» →
«Выдать подписку».

## Настройки

| Переменная окружения API | Значение |
| --- | --- |
| `TARKOV_GUARD_ALLOWLIST` | адреса, которые никогда не блокируются, через запятую |

Пороги лежат в коде:

- очки и окна — `SIGNAL_RULES`, `BAN_SCORE`, `WINDOW_MS` в `securityGuard.ts`;
- перезапуски и копии — `GUARD_THRESHOLDS` в `serverGuardian.ts`.

Их проверяют тесты:

- `server/src/routes/serverGuard.test.ts`;
- `electron/serverGuardian.test.ts`;
- `electron/siteProxy.guard.test.ts`;
- `src/components/serverGuardText.test.ts` (английские тексты).

## Чего страж не делает

- Не читает и не хранит содержимое запросов и пароли.
- Не блокирует статические страницы сайта: файлы сайта отдаются и заблокированному адресу, но API ему недоступен.
- Не подменяет защиту Cloudflare. Для сильных атак включите в панели Cloudflare режим «Under Attack» и правила WAF.
- Не восстанавливает базу автоматически.
