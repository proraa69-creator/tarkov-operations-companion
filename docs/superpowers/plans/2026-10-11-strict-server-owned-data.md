# План завершения строгого server-only зеркала

Спецификация: `docs/superpowers/specs/2026-10-11-owned-tarkov-data-mirror-design.md`  
Исходная реализация: commits `1d174c7`, `b2bc5f2`  
Назначение: закрыть оставшиеся внешние пути, добавить откат карт/изображений и усилить откат серверного релиза без перерыва production.

## Порядок включения

Миграция выполняется server-first:

1. сервер получает полное зеркало и резервные поколения, но сохраняет старый совместимый режим;
2. bootstrap и rollback проверяются на RaidNVMe;
3. server-only включается конфигурацией на VPS;
4. только после успешного smoke-check публикуется клиент без внешних fallback;
5. прежняя серверная и клиентская сборки остаются доступными до завершения проверки.

Так приложение не окажется без данных между обновлениями сервера и клиента.

## Этап 1. Усилить хранилище поколений

Файлы:

- `server/src/services/mirrorStorage.ts`;
- `server/src/services/mirrorStorage.test.ts`;
- новый `server/src/services/mirrorRollback.ts`;
- новый `server/src/services/mirrorRollback.test.ts`.

Работы:

1. Проверять manifest и SHA-256 всех обязательных файлов перед переключением.
2. Не публиковать новое поколение, если набор хешей совпадает с `current`.
3. Добавить атомарный `rollback(slot)` с обменом `current`/`previous`.
4. После публикации и отката выполнять переданный smoke-check; при ошибке публикации автоматически возвращать старый указатель.
5. Сохранять неудачное поколение до следующей успешной ротации, не выдавая его API.
6. Сериализовать publish и rollback одним lock, чтобы минутная цена не пересекалась с ручным откатом.

Тесты:

- одинаковое содержимое не создаёт поколение;
- повреждённый файл не переключает указатель;
- неудачный smoke-check возвращает прежний `current`;
- ручной rollback проверяет хеши и меняет поколения местами;
- конкурентные publish/rollback выполняются последовательно.

## Этап 2. Перевести карты и изображения на `current/previous`

Файлы:

- `server/src/services/mapMirror.ts` и тест;
- новый `server/src/services/itemImageMirror.ts` и тест;
- `server/src/routes/mapTiles.ts` и тест;
- `server/src/routes/itemImages.ts` и тест;
- `scripts/cache-item-images.mjs` и тест;
- `server/src/index.ts`.

Работы:

1. Импортировать существующие `${RAIDOS_MIRROR_DIR}/maps` и `images/items` как начальные поколения без повторной загрузки.
2. Ежедневно строить staging-поколение карт; неизменившиеся файлы копировать локально или связывать hardlink на том же RaidNVMe.
3. Ежедневно строить staging-поколение изображений после каталога; сохранять прежний корректный файл, если upstream временно отдаёт ошибку или placeholder.
4. Раздавать карты и изображения только из активного поколения.
5. Проверять обязательный `maps.json`, полноту наборов, сигнатуры файлов, размеры и хеши до переключения.
6. Ограничить пиковое место: перед началом оценивать размер текущего поколения плюс запас 3 ГБ; при нехватке не начинать staging.

Тесты:

- импорт существующего дерева не меняет URL API;
- неполная карта и повреждённая картинка не публикуются;
- старое поколение продолжает раздаваться во время загрузки;
- успешный проход оставляет ровно рабочую и резервную копии;
- traversal и файл вне manifest возвращают 404.

## Этап 3. Сделать production gateway дисковым

Файлы:

- `server/src/services/dataGateway.ts` и тест;
- `server/src/services/tarkovDataMirror.ts` и тест;
- `server/src/routes/data.ts` и тест;
- `server/src/services/catalogService.ts` и тест;
- `server/src/index.ts`.

Работы:

1. Добавить `RAIDOS_DATA_STRICT=1`: в этом режиме `DataGateway` никогда не выполняет upstream по пользовательскому запросу.
2. Сохранять ответы известных GraphQL-операций приложения по каноническому ключу запроса и переменных.
3. Включить обязательные варианты режимов и языков в суточный prewarm.
4. Неизвестный ключ возвращает контролируемый `503`; допустимая новая пара истории цен ставится в очередь следующего суточного прохода.
5. Цены всех трёх режимов обслуживать из минутных `prices-*` поколений.
6. Удалить production fallback каталога на upstream после подтверждения bootstrap.
7. При выключенном strict-режиме оставить прежнее поведение только для локальной разработки и миграционного выпуска.

Тесты:

- strict gateway не вызывает fake-upstream при cache miss;
- известные GraphQL/JSON запросы работают при полностью отключённой сети;
- запрос истории создаёт очередь, но не внешний HTTP-запрос;
- `regular`, `pve`, `pvp-season` и `ru`/`en` не смешиваются;
- пустой первичный снимок даёт 503, старый корректный снимок продолжает работать.

## Этап 4. Удалить внешние fallback из опубликованного клиента

Файлы:

- `src/data/tarkovApi.ts` и тест;
- `src/data/tarkovJsonClient.ts` и тест;
- `src/data/mapMirror.ts` и тест;
- компоненты карты, вызывающие `retryTileFromMirror`;
- `electron/main.ts` и тесты политики запросов;
- `electron/buildEdition.ts` и тест.

Работы:

1. Любая packaged-сборка, включая owner, использует gateway; direct разрешён только при `DEV` или явном тестовом флаге.
2. Удалить преобразование URL Raid OS обратно в `assets.tarkov.dev` и повтор tile/fetch во внешний источник.
3. Если серверный файл отсутствует, показывать штатное состояние недоступности или локальный IndexedDB-кэш, не менять host.
4. В Electron блокировать прямые обращения renderer к `api.tarkov.dev`, `json.tarkov.dev`, `assets.tarkov.dev` и `players.tarkov.dev` во всех packaged-редакциях.
5. Добавить статический тест, запрещающий новые внешние data/image/map URL в production-коде клиента.

Тесты:

- owner и client packaged routes равны `gateway`;
- dev route остаётся доступен только явно;
- map retry не меняет `raidos.app` на upstream;
- fake external fetch не вызывается при ошибке Raid OS;
- allowlist не блокирует обычные внешние ссылки, не относящиеся к данным игры.

## Этап 5. Откат релиза и эксплуатационная команда

Файлы:

- `electron/linux/updater.ts` и тест;
- `deploy/linux/install.sh`;
- новый `scripts/rollback-mirror.mjs` и тест;
- `scripts/build-linux-server.mjs`;
- `docs/linux-server.md`;
- `docs/subscription-protection.md`.

Работы:

1. Перед переключением Linux release сохранять прежний target симлинка и метаданные сборки.
2. После рестарта проверять локальные API/site health и публичную версию; при ошибке возвращать прежний target и повторно запускать службы.
3. Никогда не восстанавливать старую SQLite-базу поверх действующей при откате кода.
4. Включить `rollback-mirror` в Linux bundle; команда принимает slot или `--all`, проверяет manifest и печатает результат без секретов.
5. Добавить в `install.sh --check` активные/предыдущие поколения, свежесть и последний результат smoke-check.
6. Добавить systemd-настройки `RAIDOS_DATA_STRICT=1`, `RequiresMountsFor` и ежедневный image sync в поставляемую конфигурацию.

Тесты:

- неудачный health-check возвращает прежний release;
- удачный релиз не трогает базу и оставляет предыдущую сборку;
- rollback данных отказывается работать с повреждённым manifest;
- повторный rollback предсказуемо возвращает поколение вперёд.

## Этап 6. Production-миграция и выпуск

1. Выполнить server tests/typecheck, корневые tests/typecheck/lint и production build.
2. Проверить diff на токены, ключи, runtime-данные и прямые внешние клиентские URL.
3. Выпустить переходную серверную сборку со strict-флагом, выключенным по умолчанию.
4. На VPS проверить mount, свободное место и импорт существующих карт/изображений.
5. Дождаться `done` для datasets, prices, maps и images и убедиться, что есть `current`/`previous`.
6. Проверить ручной rollback на одном тестовом слоте и вернуть свежее поколение.
7. Включить `RAIDOS_DATA_STRICT=1`, перезапустить API и временно заблокировать upstream для smoke-test.
8. Проверить каталог, задания, три экономики, карты, SVG и изображения через `raidos.app`.
9. Выпустить packaged client/owner без fallback, дождаться зелёного CI и автоматической публикации.
10. Проверить публичную версию, обновление приложения и журналы release/API; предыдущие поколения и release не удалять до завершения проверки.
